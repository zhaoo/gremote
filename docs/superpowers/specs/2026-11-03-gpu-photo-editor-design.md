# GPU 照片编辑器与调色核心 V2（待确认）

## 用户目标与决定

用户实测指出：曲线交互不跟手，曝光/对比等基础调节观感失真。要求研究开源修图项目与专业产品，继续优化照片编辑。2026-11-03 用户明确选择「这轮同时全面迁移 GPU」。既有深灰、中性白、照片优先、Snapseed 式工具入口保留；样式变化先展示交互稿再实施。全部开发在 GRemote develop，保留未提交改动，不改相机协议、固件或 SD。

本设计中的性能数值均为验收目标，不是已达结果。交付平台暂定为当前真实设备 Android（23127PN0CC）；这是依据现有 APK 联调路径作出的实现选择。iOS 尚无本轮实机验收条件，继续保留可用路径，不能声称已全面迁移或验收；其平台接入需要另列验收。

## 已核实的问题

- 当前 native/imaging/src/photo_edits.cpp Basic 把 sRGB JPEG 通道直接乘 2^EV，再立刻 Clamp，后续高光无法处理超出范围的数据。实际现有 host 动态库灰阶 [64,128,192,240]，EV+1 输出 [128,255,255,255]；再把高光拉到 -1 输出 [102,255,255,255]。这说明中间层次已丢失；不代表 JPEG 原本丢失的高光可以恢复。
- 同一张1600×1067合成图，现有host原生曲线单项耗时中位13.68ms，曲线加曝光/对比55.88ms（各3次热采样）。排除Flutter、isolate复制、纹理上传和AndroidGPU，不能当真机帧率。曲线变更仍重跑未变的基础处理。
- 每次 renderPhoto 都 Isolate.run，复制整张RGBA入native并复制结果回Dart；FramePreview逐帧decodeImageFromPixels。曲线编辑同时更新整页和直方图，没有驻留纹理和按处理阶段复用的缓存。
- 基础测试曾主要证明参数会改变像素，不足以证明曝光语义、肤色稳定和明暗层次。

## 考虑过的路线

1. 保留C++逐帧CPU核心，优化缓存和分级预览：范围较小、现有预览/导出共核；跨语言大图往返与像素运算仍制约持续拖动。
2. 全面迁移照片像素处理到GPU：原图/中间结果驻留，只提交参数和曲线表；预览与导出复用同一shader图。需处理浮点精度、纹理上限、分块、上下文恢复与驱动能力。**用户选择此路线**。

GPU迁移指照片的几何、调色、LUT、曲线、光学/纹理效果、画布合成。JPEG解码/编码、EXIF、文件发布继续使用成熟CPU实现；不得把GPU预览加旧CPU导出宣称为本轮完成。

- RawTherapee curves及官方Exposure说明：曲线查找表、保留高光处理空间、避免在高光已截断后补救。https://github.com/RawTherapee/RawTherapee/blob/dev/rtengine/curves.cc ，https://rawpedia.pixls.us/exposure/

- Lightroom官方基础调节：不同明暗区域分别控制，不把“白场”实现成全局gamma。https://helpx.adobe.com/lightroom-classic/desktop/help/tone-control-adjustment.html
- 当前Flutter 3.24.5/engine a18df97ca5已核对支持SurfaceProducer；按本机SDK回调API实现，不能照抄最新版API。https://github.com/flutter/engine/blob/a18df97ca57a249df5d8d68cd0820600223ce262/shell/platform/android/io/flutter/view/TextureRegistry.java

研究与自主实现分开记录，引用来源、版本和实际采用范围；不直接粘贴不兼容许可的实现。

## 架构

Flutter编辑文档/手势 → 版本化RenderDescriptor → Android原生渲染线程/常驻EGL ES3上下文 → 同一GPU处理图 → SurfaceProducer/Texture预览或离屏FBO分块导出。

- Flutter保留编辑文档、工具草稿、撤销/重做、自动保存、导出确认与状态。图像不逐帧通过MethodChannel/FFI往返；只发送会话ID、generation、参数、小型曲线表、LUT身份与编辑事务边界。
- Android平台层管理SurfaceProducer生命周期；native渲染线程独占EGL和GL对象。主/UI线程不等GPU fence或JPEG写盘。
- 预览与导出使用同一组shader、相同处理顺序、颜色空间、归一化半径、确定性纹理种子及曲线表。导出固定已确认的RenderDescriptor，独立FBO，不读取屏幕截图。
- 曲线/参数输入按显示节奏合并，仅保留最新待处理generation。单GPU队列，不积压逐次触摸事件；取消/撤销/切图/切工具立即撤销旧结果发布权限。
- 每阶段缓存键包含源文件身份、方向/几何、算法版本、该阶段及全部上游参数、LUT内容hash、分辨率与上下文代次。更改曲线只失效曲线及下游，不能复用变更前的光晕等下游效果。
- 原图对比使用未编辑源纹理；放大查看从有足够分辨率的纹理或局部高分辨率区域取样，不能把低分辨率临时预览放大后称为细节。

### GPU能力与失败行为

启动会话检测ES版本、GL_MAX_TEXTURE_SIZE、可渲染半浮点FBO、实际shader编译与FBO完整性。Android主路径采用RGBA16F中间缓冲，数学highp。禁止在每个步骤退回RGBA8并提前丢失高光。

本轮验收机必须使用GPU预览及GPU导出。能力不足/上下文损坏时保留编辑文档并明确反馈；可保留原CPU兼容路径用于旧设备，但必须使用同版本算法并记录backend，不能只给预览或只给导出换一套效果。未完成V2兼容实现时不得静默回退旧V1。

后台/旋转/内存回收：释放失效Surface与窗口EGLSurface；上下文代次变化时丢弃旧纹理ID/缓存/异步回执，重建后由最后已确认文档恢复。后台进入不触发自动导出或任何相机调用。会话关闭等待任务排空后释放GPU/FD/纹理。

## 统一处理顺序与画质

1. JPEG解码、ICC识别/规范化、EXIF方向；正确处理sRGB输入，已标记其他色域需转换，不把AdobeRGB/P3直接当sRGB。输出以SDR sRGB为本轮目标。
2. 旋转/翻转、校正、归一化裁切和目标采样；避免每次曲线拖动重复几何。
3. sRGB解码至线性工作RGB，白平衡与曝光用浮点计算，保留临时超范围数据。
4. 基础明暗：曝光有明确EV语义；对比围绕明暗枢轴使用连续S曲线；高光/阴影使用平滑亮度权重；白场/黑场分别调整端点区域，减少相互牵连。亮度处理尽量保持色相/通道关系，避免通道独立硬截造成偏色。
5. 柔和的高光肩部与色域压缩，将浮点结果转换至显示参考域。中性参数恒等、不默认套风格；原图已经全白的JPEG不伪造纹理。
6. LUT（明确以sRGB显示域为本轮导入合同，现有cube域校验和三线性采样保留）、RGB总曲线与R/G/B独立曲线。曲线表由同一控制点模型生成，插值不额外过冲，保留用户主动绘制的反向曲线能力。
7. 光晕/柔光多pass、暗角、褪色/黑白、漏光、颗粒；全局归一化坐标/固定种子，强度0不改变画面。半径与最终照片长边对应。
8. GPU画布/边框合成。文字仍由既有FramePainter生成透明overlay作为纹理输入，同一几何用于预览与导出。
9. 最终一次输出编码至sRGB/RGBA8；导出只在最终tile读取像素给JPEG编码，不将半成品回传Dart。EXIF/GPS保留开关、取消和原子发布沿用。

算法数值定义先以灰阶阶梯、色块/肤色夹具制定合同，再实现shader与CPU参考。不得按单张图调整到“看起来不错”后当作通用算法，也不承诺复制Lightroom专有算法。

## 大图导出与一致性

- 支持现有原尺寸/2560/1440、裁切、边框和EXIF流程。6000×4000及超过单纹理上限的长图必须走分块，不静默缩小。
- tile坐标基于完整最终图像；grain/leak不以tile原点重置。blur/halation使用足够邻域halo和同一分辨率规则；不能简单切块造成接缝。极大半径需统一多尺度处理图，halo资源无法满足时明确失败，不使用不同算法替代。
- 几何采样在全图坐标中计算，横跨tile边界时不重复取整。边框/文字也按全局画布定位，旋转/EXIF与裁切尺寸沿用float32边界合同。
- 导出冻结document版本、参数、LUT和种子；不允许导出时持续拖动改写本次结果。不覆盖原图，完整成功后才发布系统相册项；取消/失败清理临时文件和GPU资源。
- 验证GPU同尺寸预览离屏buffer和GPU导出JPEG解码结果，而不是仅验证shader源码相同。额外比较GPU与CPU参考，以定位精度/色彩空间差异。

## 数据版本与旧编辑

引入明确processVersion：V1保留既有编辑解释，V2为新调色。旧JSON缺失版本按V1读取，新编辑默认V2；预设也携带版本。旧照片不得因升级App自动改变已保存外观。

旧编辑可从更多菜单选择使用新版调色：提供转换前后预览并确认，作为一个可撤销操作；不自动改写曝光参数以猜测原意。保存、导出、LUT缩略图、历史及预设均绑定processVersion。V1 GPU兼容输出必须对照旧C++夹具。开发期间可保留明确旧版路径；若本轮Android的V1输出尚不能由GPU复现，就不能报告“全面迁移完成”。V1与V2都纳入Android预览及导出验收，允许保留CPU参考后端供测试与已明确的兼容处理，不将它计入GPU验收。

## 交互稿的变化

沿用已确认的视觉风格，只打磨基本工具与曲线。照片区不显示GPU/线程/分辨率等实现术语。

- 基础：底部参数横排可滑动，当前参数名/数值、滑杆；双击数值归零；零点轻触感与精调模式，尊重系统触感和减少动态效果。滑动照片调整参数不与双指缩放竞争。
- 曲线：更大的有效操作区，RGB/R/G/B精简切换，控制点扩大不可见触摸热区；控制点位置立即随手指绘制，不等照片处理完成。支持轻点添点、拖动、删除中间点、撤销/重做及单通道重置；拖动时与外层滚动互斥，增加输入/输出数值的精确调整入口。
- 直方图基于真实像素/固定输入阶段，后台按较低频率更新，不能阻塞拖动或为每次触摸重扫整张图。曲线图本身不做弹簧动画/位置滞后，面板进出使用短轻动效。
- 按住对比、工具取消/完成、编辑记录、所有16项工具入口、LUT导入、边框日期和分享导出都保留。新视觉稿只展示基础/曲线/精调这几个变化，不重新设计首页或相机页。

## 验收目标与证据

功能/画质：中性恒等；EV阶梯；高光可压回人为曝光产生的溢出；灰阶/肤色/高饱和色/夜景/天空连续渐变无明显断层和异常色相；明暗控件方向正确、作用区域合理；极值不会NaN、崩溃或黑图。使用一组真实GR JPEG和合成夹具，不用AI生成图片当算法证据。画质需用户查看样张确认。

交互（真实Android设备，release/profile包，预热后）：曲线控件跟手以60Hz、UI frame p95≤16.7ms为目标；持续调节照片更新目标≥30fps、输入到可见画面p95≤50ms；停手后最终清晰帧目标≤150ms。首次载入单列。报告实际达成值，未达就继续定位，不把host基准或Debug时序当结果。复杂多效果叠加单独测量。

一致性：同尺寸GPU buffer预览与导出编码前buffer逐像素一致；JPEG质量100与预览平均RGB误差目标≤1/255，报告最大值和异常点。纹理/不同尺寸采样另测，不承诺缩略图与24MP图逐像素相同。全图/分块输出、tile接缝/光晕边界必须对照；固定seed重复导出稳定。

稳定性：至少24MP原图、横竖/旋转/EXIF6、极端长图、零强度、任意曲线、坏LUT、后台恢复、旋转、连续撤销/取消、导出取消、低内存与Surface销毁。记录显存/进程内存峰值、GPU信息、发热后的持续性能及设备/包/源码身份，不写虚构数值。相机和照片传输行为不受影响。

## 开发顺序（设计确认后细化实施计划）

A. 灰阶/真实样张画质合同、性能基线、processVersion与渲染描述符。
B. Android EGL/SurfaceProducer驻留会话、参数合并与上下文生命周期，真实GPU中性往返。
C. 基础调色V2、LUT/曲线GPU及精调交互；先验证手感与样张，再接后续效果。
D. 其余现有工具全部GPU化、帧画布合成、原尺寸分块导出与一致性回归。
E. 保留旧记录/预设、全部错误/取消/资源释放；完整测试与真机安装，用户验收后才讨论发布。

阶段候选可供检查，但C阶段不算全面迁移完成。验收前不推送main、不部署网站、不刷相机；本任务只涉及手机App。
